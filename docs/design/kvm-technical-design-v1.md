# 跨平台 USB KVM：技术设计与 Implementation Spec

版本：1.0  
日期：2026-09-07  
交付性质：设计与实现规格，不包含应用实现代码。文中的性能数字是验收目标，不是已经测得的结果。

## 1. 产品边界与最终技术决策

本项目实现一个本地 KVM：控制端通过 UVC 采集卡显示被控机 HDMI 画面，通过串口向 CH9329 发送键鼠控制。被控机不安装代理程序。首版只管理一张采集卡、一个串口和一个控制窗口。

首版包含设备选择、采集模式选择、实时预览、窗口化与无边框全屏、键盘输入、绝对/相对鼠标、三键鼠标与垂直滚轮、明确的控制接管/释放、必要的异常恢复、配置保存和诊断信息。

不使用 Qt、Electron、Tauri 或 WebView；不以其他 UI 框架作为平台适配的隐藏依赖。

首版不包含音频、录像、截图管理、网络串流、远程控制服务器、账号系统、多路 KVM、剪贴板同步、文件传输、虚拟磁盘、ATX 电源控制、宏系统、手柄、多媒体键、鼠标侧键、HDR、交错视频处理及 4K 性能保证。设备已有的 EDID、缩放、HDCP 行为不由本应用改造。

### 1.1 推荐技术栈

| 事项 | 本规格的决定 |
|---|---|
| 语言和构建 | 使用 C++20、CMake、Ninja，采用 vcpkg manifest 管理第三方依赖。 |
| 窗口、事件与鼠标捕获 | 使用 SDL3，不自行重写跨平台窗口系统。 |
| 界面 | 使用 Dear ImGui 官方 SDL3 平台后端和 OpenGL3 渲染后端。 |
| 图形基线 | 三个平台统一采用 OpenGL 3.2 Core、GLSL 150；macOS 创建 forward-compatible core context。 |
| 采集设备接入 | Windows 使用 Media Foundation；Linux 使用 V4L2；macOS 使用 AVFoundation。三个实现只负责设备和采集，不负责界面或键鼠。 |
| 视频处理 | 使用 FFmpeg 的 libavcodec、libavutil、libswscale。原始帧绕过解码；MJPEG 使用 libavcodec。 |
| 串口 | 使用 libserialport，并在项目内实现 CH9329 协议和调度。 |
| 辅助依赖 | 使用 nlohmann/json 保存配置，spdlog 输出低频诊断，glad2 加载应用侧 GL 函数；Catch2 仅用于测试。 |

Dear ImGui 已有上述官方后端，直接集成而不修改其事件实现。[S3] libserialport 是独立的跨平台串口库，不需要引入 sigrok 其余部分。[S11]

**这里有意不把 libavdevice 作为生产采集入口。** FFmpeg 仍然是视频处理核心，但模式枚举、驱动缓冲、阻塞取消和热插拔属于设备接入问题。三个薄的原生适配器可以把这些行为写成明确合同，而不依赖不同 FFmpeg 设备后端恰好具有相同的缓冲和退出语义。

这不是同时维护三套视频 pipeline。系统 API 到达“应用拥有的 Raw/MJPEG 样本”后，后面只有同一条 FFmpeg/渲染路径。

OpenGL 在 macOS 已被弃用，因此它是首版的实现选择，而非对未来平台支持的永久保证。[S7] GL 代码集中在渲染目录；将来替换为 Metal 或 SDL GPU 时，不改采集、输入和 CH9329 层。首版不实现第二个图形后端。

### 1.2 平台和硬件验收基线

正式验收覆盖 Windows 11 x64、Ubuntu 24.04 x64 的 X11 与 Wayland 会话，以及 macOS 14 或更新版本的 Apple Silicon 机器。Intel macOS 可以生成构建，但未经过实机测试不得标为已验收。其他平台组合属于后续扩展，不阻塞首版。

1080p60 是主要视频目标，以采集设备实际枚举能力为前提。首版允许逐行、8-bit SDR、尺寸不超过 1920×1200、帧率不超过 60 fps 的模式；1920×1200 仅属于兼容范围，不额外承诺其 60 fps 性能。首版也需要处理设备暴露的常见较低分辨率和 4:3 模式。不得把“MS2130/MS2131”芯片名称等同于某个固定的分辨率、帧率或 USB 传输格式。

CH9329 必须处于二进制协议模式，USB 侧配置包含键盘和鼠标，串口连接必须能接收应答。软件不默写芯片 EEPROM，不自动更改 VID/PID、工作模式或供电设置。

## 2. 模块划分

整体只有应用、视频、输入和串口控制几个直接相连的模块。没有插件系统、通用媒体图、服务容器、事件总线或进程间通信。

| 模块 | 职责 | 不应承担的职责 |
|---|---|---|
| Application / KvmSession | 协调设备连接、控制状态、用户操作和关闭顺序。 | 不解析协议，不处理像素。 |
| CaptureSource | 枚举设备和模式，打开/停止采集，输出完整且拥有内存的样本。 | 不解码，不访问 ImGui，不发送串口。 |
| VideoProcessor | 解码 MJPEG、规范化原始帧描述，输出 VideoFrame。 | 不调窗口 API，不按媒体时间轴等待。 |
| VideoRenderer | 上传平面、执行颜色转换、维护视频纹理、交给 ImGui 显示。 | 不知道串口、设备路径或控制协议。 |
| InputRouter | 判断事件归属，执行接管/退出，转换物理键码和视频坐标。 | 不拼 CH9329 字节，不等待串口。 |
| Ch9329ControlSink | 接收有序控制事件，维护 HID 状态，合并允许合并的运动，完成串口事务。 | 不包含 SDL 或 ImGui 类型。 |
| Config / Diagnostics | 保存明确的用户设置，记录状态和性能计数。 | 不记录用户实际键入的内容。 |

只建立两个有实际替换需求的接口：`CaptureSource` 和 `ControlSink`。其余模块使用普通具体类和组合。`CaptureSource` 的三个平台实现以及测试假设备共享同一合同；`ControlSink` 的本地实现和测试替身共享同一合同。

UI 可以依赖各模块的公开状态快照；采集、视频和控制模块不得反向依赖 UI。不要为了“将来可能有远程”给每个类再包一层接口。

## 3. 数据合同与所有权

### 3.1 DeviceInfo / CaptureMode

`DeviceInfo` 包含后端类型、设备稳定标识、显示名称和可选的 USB 元信息。`CaptureMode` 包含设备标识、尺寸、有理数帧率、设备提供的格式，以及应用收到的格式。传输格式未知时明确写 unknown，不猜测。

设备格式、解码输出格式和显示纹理格式是三个不同字段。尤其不能把 macOS 输出 NV12 的事实解释成 USB 总线上一定传输 NV12。

### 3.2 CaptureSample

每个样本包含 `generation`、单调递增的 `sequence`、控制端单调时钟下的到达时间、可选设备时间戳及其 time base、尺寸、SAR、色彩信息，以及 Raw 或 MJPEG 负载。

Raw 负载描述像素格式、各平面偏移和 stride；MJPEG 负载是一幅完整 JPEG 图像，而不是任意 USB 分片。负载必须由应用拥有，或者由其持有的明确引用计数对象拥有。

**禁止把已经归还驱动的 mmap 地址、已经 unlock/release 的 CVPixelBuffer 地址，或已经释放的 MF sample buffer 地址交给后续线程。** 首版接受从驱动到应用的一次拷贝。该拷贝换取简单的生命周期和可停止采集；不做跨平台零拷贝。

MJPEG 缓冲需要额外分配并清零 AV_INPUT_BUFFER_PADDING_SIZE 指定的尾部空间。单幅压缩负载上限为 16 MiB，单幅原始缓冲（含 stride padding）上限为 64 MiB，尺寸还必须满足首版模式上限。采集适配器必须验证 stride、平面边界和实际 payload 长度；VideoProcessor 在解码上下文设置相应 max_pixels 限制，并校验解码后的尺寸。异常尺寸和整数溢出直接拒绝，不能根据设备元数据无上限分配内存。

### 3.3 VideoFrame

`VideoFrame` 持有只读、引用计数的 `AVFrame`，并保留样本的 generation、sequence、到达时间、设备时间戳、颜色信息，以及解码完成时间。

采集序号和视频帧序号保持可追溯关系。渲染者持有引用期间，生产者不得改写其像素。需要复用 AVFrame 容器时必须转移或增加引用，而不是复用仍在使用的底层缓冲。[S4]

`VideoFrame` 不包含 OpenGL、SDL、ImGui 或平台原生对象。该边界既用于本地渲染，也可作为未来编码器的输入。

### 3.4 ControlEvent

控制事件只表达键鼠语义，包含控制 session 的 epoch、sequence、控制端单调时间戳和一种事件负载：键盘 usage 按下/释放、绝对位置、相对位移、鼠标按钮变化、垂直滚轮，或 ReleaseAll。

键盘使用 USB keyboard usage 语义；绝对坐标使用归一化的 `[0,1]`；相对位移保留有符号精度和小数残差。绝对模式的鼠标按钮和滚轮事件必须携带事件发生时的视频坐标，避免点击使用过期位置。

`ControlSink.submit` 不阻塞 UI，并返回 accepted、not-ready 或 overloaded。`releaseAll` 使用独立紧急标志，不会因为普通队列已满而失败。控制状态的完成通知通过状态快照或小型结果队列返回，不能回调进入 ImGui。

采集 generation 与控制 epoch 是两个独立计数。重新连接或切换采集配置改变前者；每次接管、释放或控制故障改变后者。

## 4. 线程与队列

应用显式管理四个执行线程。系统框架自己的回调线程不计入这四个线程，也不能在那里做重任务。

| 线程 | 工作 | 可以等待什么 |
|---|---|---|
| 主线程 | SDL 事件、InputRouter、ImGui、全部 OpenGL 操作、更新 UI 心跳。 | 有界的事件等待和图形提交；不能等待采集或串口事务。 |
| Capture 线程 | 设备枚举/配置/生命周期；Linux poll 采集循环；协调 Windows/macOS 异步回调。 | 可取消的设备等待、生命周期命令。 |
| Video 线程 | 消费最新样本，解码/整理帧，发布最新 VideoFrame。 | 等待新样本或停止通知。 |
| Serial 线程 | 独占串口、协议解析、输入队列、ACK/超时和释放 watchdog。 | 有短超时的串口等待和输入通知。 |

Windows/macOS 的采集回调只做验证、复制、发布和必要的 re-arm。macOS 的采集 session 生命周期使用专用串行调度，不在主线程调用可能较慢的启动/停止操作。

使用普通 mutex、condition_variable、原子停止标志和 RAII。使用 `std::thread` 即可，不因 C++20 而强制引入协程或自制 lock-free 队列。

### 4.1 视频方向：两个单槽 mailbox

采集与处理之间放 `LatestSample`，处理与渲染之间放 `LatestFrame`，容量都为 1。发布新对象时替换尚未消费的旧对象；消费使用短锁交换引用；大对象析构和像素处理在锁外完成。

这两处丢弃的是不同阶段的待处理对象。已经开始解码的一帧可以完成，但不继续消费其后积压的历史帧。系统资源不足时下降的是实际显示帧率，而不是不断增长的延迟。

Raw 和独立 MJPEG 图像允许这样丢弃。未来接入有帧间依赖的编码流时，不允许把此规则直接套到压缩包上；需要在解码后丢帧或使用理解参考关系的恢复策略。

设备缓冲、两个 mailbox、当前工作帧和 UI 当前帧的持有者必须能逐个列出。不得出现隐藏的无界 vector、任务队列或“每帧创建一个异步任务”。

### 4.2 控制方向：有界、有序队列

普通控制队列最多 128 个语义事件。键盘边沿、按钮边沿和滚轮事件是顺序边界；不能像视频一样只保留最新状态。

只合并连续、相邻、同 epoch 且中间没有顺序边界的纯运动：绝对运动保留最后坐标，相对运动累加位移。滚轮首版不跨事件合并。绝对按钮事件可以把自身坐标与按钮变化装进同一个鼠标报告。

队列满，或最老待处理事件超过 100 ms 时，退出接管、清空未执行旧事件、提高 epoch，并安排 ReleaseAll。不能静默丢掉某个 key-up 继续控制，也不能排队数秒后补发一串旧操作。

ReleaseAll 是唯一允许越过普通事件顺序的操作。它先废弃全部尚未执行的旧事件；已写入串口、正在等待应答的一个事务无法撤销。

## 5. 视频采集实现

### 5.1 设备选择和格式协商

设备稳定标识优先使用 Windows MF symbolic link、Linux `/dev/v4l/by-id` 和 macOS AVCaptureDevice uniqueID。缺少持久标识时保存可用的 USB 序列号/拓扑与名称组合，并将匹配标记为弱匹配。

不得只保存“第 0 个摄像头”，也不得在设备消失后自动选择另一台同名设备。多个匹配对象需要用户确认。

首次模式选择顺序为：1080p60、720p60、1080p30、720p30，之后在实际枚举集合内选择不超过首版能力的模式。59.94/29.97 归入相应帧率等级，但保存并使用原始有理数。已保存且仍有效的用户模式优先于默认规则。

同一尺寸/帧率下，优先选择设备可直接交付的 YUY2/UYVY，其次 NV12，再其次 MJPEG；BGRA 是允许的原生 API 输出。若系统不能控制总线格式，则只对实际可选项排序。显式手动选择失败时直接报告，不默默切到其他模式。

自动模式可以在打开失败或持续异常时尝试下一个候选；状态栏必须显示最终实际模式。不要只显示请求了 60 fps，而隐藏设备实际交付 30 fps。

以 1080p60、每像素 2 字节计算，原始 4:2:2 数据量约为 `1920 × 1080 × 60 × 2 = 248,832,000 B/s`，尚未计入协议开销。这说明分辨率、USB 链路和格式必须一起判断，不能仅按画质选格式。

### 5.2 Windows：Media Foundation

使用视频设备源与异步 Source Reader。Capture 线程负责 COM/MF 生命周期和配置；通过异步 callback 接收 sample，检查同步调用结果及 callback 的 HRESULT。[S8]

只启用视频 stream，先枚举 native media type，再设置明确类型。关闭 Source Reader 的软件视频处理和不必要的转换；不要为预览先强制转换到 RGB、增加缩放或去交错。需要原始 MJPEG 时请求该原生类型，再交给应用的 FFmpeg 解码。

每次只维持一个未完成的 ReadSample 请求。回调复制完整有效 sample 后立即发布并继续请求；不得在回调解码或等待 UI。

对 stride、底部向上的 RGB 缓冲和格式变化标志进行处理，必要时使用 IMF2DBuffer 获得二维布局。停止时先停止 re-arm，再 Flush，等到回调/flush 完成后释放 SourceReader 和 MediaSource。callback 的存活期必须覆盖所有可能到达的回调。

### 5.3 Linux：V4L2

采用 `O_NONBLOCK`、MMAP streaming 和 poll。申请 3 个驱动缓冲，记录驱动实际返回数量；返回数量不同不是自动报错，但最低可工作数量必须按驱动结果处理。[S9]

一次唤醒后取走已经完成的缓冲，丢弃较旧完成帧，复制最新完整帧，再及时 QBUF。按 bytesused、bytesperline 和 plane 元信息访问，不能假定每行紧密排列。首版面向常见 UVC 单平面采集节点；多平面专用设备可明确列为不支持。

poll 同时监听采集 fd 和停止 eventfd，避免设备无帧时无法退出。先结束工作循环并执行 STREAMOFF，再在没有任何借用者的情况下 unmap 和关闭 fd。设备移除和 EIO/ENODEV 等错误进入会话恢复流程。

### 5.4 macOS：AVFoundation

平台代码放在少量 `.mm` 文件中，使用 AVCaptureSession 和 AVCaptureVideoDataOutput。选择设备支持的 activeFormat 和帧率范围，关闭不需要的输出，尽量请求 NV12/UYVY；不支持时允许 BGRA。

设置 `alwaysDiscardsLateVideoFrames = true`，其作用是丢弃无法及时交付给 delegate 的视频帧。[S10] Delegate 只做受控复制和发布，不能持有一长串 CMSampleBuffer。

在 `.app` 中提供 NSCameraUsageDescription，并正确处理首次授权、拒绝授权和权限改变。[S12] 本地 UVC 采集不是对控制端屏幕进行录屏；不要为了采集卡引入系统屏幕录制流程。

启动、停止和切换设备在 session 串行执行环境完成。停止后使回调队列静默，并用 generation 丢弃晚到消息；不得先销毁回调会访问的 C++ 对象。

### 5.5 视频失效与模式变化

500 ms 没有收到完整新样本即标记画面停滞，并释放正在进行的控制。可以保留最后一幅图作背景，但必须显著覆盖“画面已停滞”状态，不能把静止旧图呈现成仍可安全控制的实时画面。

采集卡持续输出自己的“无信号”画面时，软件仍然会收到帧。没有设备提供的状态证据，就不能声称已经可靠检测 HDMI 无信号。

格式发生变化时提高采集 generation，先使控制退出，再重建必要的解码/纹理资源。只接受当前 generation 的帧。被控机 HDMI 模式变化未必改变 UVC 输出模式，以实际采集 API 反馈为准。

## 6. FFmpeg 处理与显示

### 6.1 解码

原始帧直接包装为拥有有效引用的 AVFrame，不进行假解码。MJPEG 使用 `avcodec_send_packet` / `avcodec_receive_frame`，正确处理 EAGAIN 和输出消费，不把 sleep 当作推进解码器状态的方法。[S4]

首版 MJPEG 从单解码线程开始，避免 frame threading 额外缓存。只有性能数据证明解码成为瓶颈时才调整线程配置，且调整后必须重新验证排队延迟。

无音视频同步，没有“按 PTS 等待显示”的播放器时钟；帧准备好后立即成为可显示候选。设备 PTS 保留用于诊断，不用于让一幅旧帧等到某个呈现时刻。

### 6.2 像素格式和颜色

渲染快路径支持 YUY2/UYVY、NV12、8-bit planar YUV420/422/444，以及 BGRA/RGBA。MJPEG 解码得到的全范围 YUV 必须保留颜色范围信息，不能一律按 limited range 解读。

对不在快路径内但首版允许的格式，libswscale 转成受支持格式，并在诊断面板标明 CPU fallback。常规 YUY2/NV12 不能默认每帧先在 CPU 转成 RGB。

颜色转换优先使用帧元数据。缺失时使用明确的默认：HD 采用 BT.709，SD 采用 BT.601；MJPEG 优先使用解码器给出的 range，其余未知 YUV 默认 limited。提供手动矩阵/range 覆盖，状态中显示“自动值/推断值/用户覆盖”，避免把推断当成设备事实。

正确处理行跨度、负 stride、UV 排列、平面尺寸、采样范围和图像方向。颜色参考测试使用同一组参数下的 libswscale 结果；不引入 HDR tone mapping 或完整 ICC 管理。

### 6.3 OpenGL 渲染路径

VideoRenderer 在主线程上传原始平面，用一个颜色转换 pass 生成源分辨率的 RGBA 纹理，再把该纹理交给 ImGui。先完成源分辨率转换，再由显示阶段缩放，避免 packed 4:2:2 在窗口缩放时采样错误。

纹理和 FBO 在格式变化时重建，平时复用。正确设置 unpack alignment / row length。所有资源删除也在 GL context 所在线程完成。

首版不实现硬件解码、PBO 流水线、DMA-BUF/CVMetalTexture 零拷贝和 GPU→CPU 回读。不得在每帧调用 glFinish。先测量现有上传和转换，再决定是否需要更多优化。

显示只做保持宽高比的 fit-contain，并正确考虑 SAR。首版不做任意裁剪、缩放平移或用户旋转，减少鼠标坐标语义。

### 6.4 UI 循环

每轮先处理 SDL 事件并投递输入，再获取最新帧、更新必要纹理和绘制 UI。键鼠不会等待下一张采集帧。

默认关闭 VSync，采用事件驱动加最大 120 Hz 的绘制上限。没有新视频和 UI 变化时不反复提交同一画面；状态指标刷新 5 Hz 即可。接管时主线程的主动等待不超过 2 ms，不允许无等待的空转循环。

提供 VSync 兼容性开关。窗口合成器或驱动仍可能引入等待；关闭 swap interval 不是绕过 macOS/Wayland 合成器的保证。实测 present 阻塞必须进入诊断，而不是隐藏在“软件延迟”外。

## 7. 输入接管和窗口交互

### 7.1 状态机

界面控制状态为 Preview、Arming、Captured、Releasing、Fault。Captured 额外带 Absolute 或 Relative 模式。

Preview 下所有操作属于本地 UI。用户在真实视频矩形内按下激活鼠标按钮后进入 Arming；吞掉这一次按钮的按下和释放，不把它变成被控机点击。等待激活按钮释放、串口 ready、画面新鲜且必要清零完成，才进入 Captured。

进入前已经按住的键加入隔离集合，只有先见到释放、再发生新的按下，才允许转发。不得因为接管时 Ctrl 已经在本机按住，就向目标补发一个不受控的 Ctrl。

Captured 下禁用本地设置控件、文本输入、菜单快捷键和 ImGui 键盘导航；只有释放键和明确的本地释放操作生效。事件仍交给官方 ImGui backend 维护 bookkeeping，但 Captured 期间只绘制非交互内容；InputRouter 使用自己的明确路由状态，不以 WantCaptureMouse/WantCaptureKeyboard 作为唯一判断。捕获期间本机光标的显示/隐藏由 InputRouter 管理，ImGui 不得覆盖它。返回 Preview 前清理接管期间残留的 ImGui 按键、鼠标和导航输入，并吞掉用于退出的 Host key 后续释放事件，避免旧输入突然触发本地控件。

### 7.2 Host key 和系统快捷键

默认释放键：Windows/Linux 使用右 Ctrl，macOS 使用右 Command。界面持续显示当前绑定；允许在 Preview 下修改绑定。释放键从不转发给目标，Esc 默认正常转发。

接管时尝试 SDL keyboard grab；相对模式启用 SDL relative mouse mode；绝对模式尝试窗口鼠标 grab/约束。SDL 的 keyboard grab 并不能截获所有系统组合键，例如 Windows 的 Ctrl+Alt+Del。[S5][S6] 任一 grab 失败均要显示实际能力，不能只修改界面状态后假装已经捕获。

不安装全局键盘钩子，不增加管理员常驻服务。被本机系统保留的组合键通过本地“发送特殊按键”菜单注入目标。首版只实现 Ctrl+Alt+Del、Alt+Tab 和发送当前 Host key，不做宏编辑器。

特殊组合仅在 Preview、目标状态已清零时发出。它们是有界的按下/释放序列，使用同一 ControlSink；可为人工触发的合成点击设置 20 ms 按下驻留，不能给普通物理输入统一增加该延迟。任何中途取消都走 ReleaseAll。

### 7.3 鼠标离开和拖动

坐标命中只使用真实视频矩形，不包含工具栏、边框和黑边。UI 的逻辑坐标与鼠标事件保持一致，drawable 像素只用于 GL viewport；不要把 HiDPI 缩放应用两次。

未发生目标按钮按下时，视频矩形外的鼠标按下不转发。目标拖动过程中离开矩形时，绝对坐标夹到边缘；对应 button-up 无论在何处收到都必须转发。焦点丢失则直接 ReleaseAll。

Captured 状态下进入工具栏不会激活本地控件。用户必须先释放控制再操作设置，从根本上避免一次点击同时作用于目标和本地 UI。

## 8. 键盘和鼠标语义

### 8.1 键盘

使用 SDL_Scancode 对应物理键，不使用字符、SDL_Keycode 或 SDL_TEXTINPUT 映射远端键盘。SDL 的标准键盘 scancode 使用 USB keyboard usage 定义，但仍需维护显式支持表，不能把所有枚举值截断成一个字节。[S13]

普通按键按事件边沿发送。忽略控制端产生的 key repeat；被控机根据持续按下的 HID 状态自行重复。短于一帧的视频间隔内完成的 key-down/key-up 也必须保留两个事件。

左右 Ctrl、Shift、Alt、GUI 分别维护。目标键盘布局决定字符解释；控制端中文输入法的提交文本不转成假按键，中文输入使用被控机自己的输入法。Caps/Num/Scroll 状态可以显示，但不主动把目标锁定状态改成本机状态。

CH9329 普通键盘采用 8 个 modifier 加 6 个普通键的报告结构。[S1] 首版采用确定的六键接纳规则：先到的六个普通键进入报告，第七个普通键在本次物理按住期间忽略并提示；即使之后空出槽位，也不突然补成一个按下。松开后再次按下才重新参与接纳。

### 8.2 绝对鼠标

绝对模式是桌面操作默认值。令真实视频矩形为 `(x0,y0,w,h)`，先计算并夹取归一化坐标：

`u = clamp((x-x0)/w, 0, 1)`，`v = clamp((y-y0)/h, 0, 1)`。

CH9329 协议使用 4096×4096 的绝对坐标空间。[S1] 本实现采用 `X = min(4095, floor(4096*u))`，Y 同理，小端编码。按设备实际显示方向映射，不重复翻转。四角、边缘和不同长宽比都要用实机命中测试验证。

绝对设备映射到目标哪个屏幕由目标系统决定。目标有多显示器、只采集其中一个 HDMI 输出时，不承诺自动知道整个桌面布局。首版提供相对模式作为明确退路，不加入远端屏幕探测或校准向导。

### 8.3 相对鼠标

使用 SDL relative mouse mode 获取连续相对运动，不采用每帧把本机光标 warp 回中心的方式。[S6] 默认增益为 1，允许一个简单的灵敏度设置；显示窗口缩放不改变相对鼠标灵敏度。

内部保留小数位移残差，输出报告时取整数。超过单报告范围的位移拆分发送；每段限制为 -127 到 127，累计和保持不变。不得把超过范围的增量直接截断后丢失余量。

每个相对报告携带当前按钮掩码。按钮边沿不能跨越运动累积段重排，保证拖动的起止位置语义。目标系统仍可能施加鼠标加速，首版不试图通过 CH9329 绕过它。

### 8.4 按钮和滚轮

首版支持左、右、中三个按钮和垂直滚轮。[S1] 滚轮使用有符号步数；高精度输入保留不足一步的残差，按 SDL 的方向标志归一化一次，不重复翻转。单报告滚轮范围同样限制为 -127 到 127，大值分段。

切换绝对/相对模式前必须先退出接管并释放旧模式状态。SDL 模式切换前后的陈旧运动事件不得被当作新的控制运动。

## 9. CH9329 协议和串口调度

### 9.1 协议子集

实现以厂商二进制通信协议为依据，字段和应答见 [S1]。以下表是首版实际需要的协议子集，不实现其余配置和自定义 HID 功能。

| 请求 | CMD / LEN | DATA |
|---|---|---|
| 查询信息 | 01 / 00 | 无。信息应答的 DATA 长度为 8。 |
| 普通键盘 | 02 / 08 | modifier、00、六个 usage。 |
| 绝对鼠标 | 04 / 07 | 02、buttons、Xlo、Xhi、Ylo、Yhi、wheel。 |
| 相对鼠标 | 05 / 05 | 01、buttons、dx、dy、wheel。 |
| 读取配置 | 08 / 00 | 只用于诊断当前设置，不写配置。 |

帧结构为 `57 AB | ADDR | CMD | LEN | DATA | SUM`；SUM 是之前各字节求和取低 8 位，LEN 最大 64。普通成功应答命令为请求 CMD 或上 80，异常应答或上 C0；HID 应答还需检查状态码。默认地址 00，可由用户明确修改；运行中不用无应答的广播地址。[S1]

解析器是增量状态机：处理任意分片/粘包、长度限制、校验失败、噪声重同步和异常命令；最大完整帧为 70 字节，接收缓存必须有界。不要假定每次串口 read 恰好得到一整帧。

GET_INFO 的 USB 枚举状态与串口已打开是不同状态：串口打开但目标 USB 未枚举时，可以保持监测，但禁止接管。未知版本号先显示兼容性告警，只有结构正确的握手、目标 USB 状态和清零报告均经过验证才允许 Ready；不能把示例中的版本号当作唯一合法版本。畸形应答或不兼容配置显示具体错误，不继续盲发键鼠。

### 9.2 连接与波特率

无历史配置时，首次连接使用 9600、8N1、无流控；只打开用户选中的端口。连接后读取信息与必要配置；目标 USB 尚未就绪时只保持监测，确认就绪后执行输入清零，成功后再进入 Ready。

低延迟运行建议预先把硬件设为 57600；只有确认 CH9329 本体的供电和版本支持时才使用 115200。WCH V1.1 手册明确说明其 3.3V 供电情况下不支持 115200。[S2] USB 转串口模块的逻辑电平标称不等于已经确认 CH9329 的 VCC。

应用中的波特率选择只改变本地端口参数，必须与芯片当前设置相符；不自动修改芯片 EEPROM。硬件预配置使用厂商已有配置方式，属于首次硬件接入步骤，不在首版增加芯片配置编辑器。

9600 保留为可用兼容模式，但明确显示性能降级。不得通过盲目切到高波特率来制造“连接成功”的假象，也不扫描并写入其他串口设备。

### 9.3 串口事务

Serial 线程独占打开、读、写、parser 和关闭。使用非阻塞读写或短超时等待，处理部分写入；一次只允许一个命令在途。写完后等待对应应答，收到后立即推进下一事务，而不是阻塞 UI。

选择单在途是为了维持可判断的完成顺序。协议没有应用层事务序号，首版不做多命令并行窗口，也不依赖几百毫秒后才能发现错误的盲发模式。

只要串口存在部分写入，就必须记录当前偏移；不能重写完整包造成重复头，也不能启动下一包。ACK 表示协议层命令状态，不代表目标应用已经处理按键或新画面已经到达。

鼠标纯运动默认合并上限为 125 Hz；9600 下上限为 30 Hz。它们是上限，不是保证速率。实际发送还受 ACK、线速和已读取的芯片时序配置约束。键盘/按钮边沿不等待鼠标合并定时器，但不能绕过前面的语义边界。

以一个绝对鼠标请求及其短应答共 20 字节、8N1 计算，仅串行传输约需要：9600 下 20.8 ms，57600 下 3.47 ms，115200 下 1.74 ms；这些数字尚未包括 USB 串口和芯片处理。因此不能把 9600 模式称为 125 Hz 鼠标链路。

不为每个输入报告硬编码 20/50 ms sleep。保留一个诊断用最小帧间隔设置，默认 0 表示除应答和硬件配置限制外不额外等待；若硬件实测要求额外间隔，记录在硬件验收报告中。

仅在空闲时查询 GET_INFO，间隔不少于 1 秒；交互期间不让状态轮询抢占控制发送。日志默认不打印每个按键或每个鼠标包。

### 9.4 超时、错误与释放

正常路径出现 100 ms 未完成事务时，标记控制停滞并退出接管，不再累积新输入。仍保持对该事务的识别和接收，至厂商协议给出的 500 ms 失败边界。[S1] 在 100—500 ms 内收到迟到有效应答，完成旧事务后只允许执行清零，不重放已废弃输入。

达到硬超时后，终止旧会话，清除未写入数据，关闭并重新建立串口会话。重新握手前等待旧应答期限结束并排空输入；不把旧会话的 HID 应答解释为新会话命令的完成。握手以不同类型的 GET_INFO 请求恢复判断，成功后再次清零，仍需用户重新接管。

相对位移和滚轮在 ACK 丢失后绝不自动重发，因为目标可能已经执行，重发会造成额外移动/滚动。其他控制事件也不采用无限重试。恢复意味着清零并建立新状态，不是继续重放旧队列。

释放先清空旧队列和逻辑状态，再发送键盘空报告和需要清零的鼠标报告。正常会话按最近使用的鼠标模式清零，绝对报告保留最后坐标，相对报告位移/滚轮为零；模式切换时先确认旧模式释放。初次连接或异常重连无法确信目标状态时，清零两种鼠标报告；此时绝对坐标可能使光标重新定位，应在交互说明中说明。

出现正常焦点丢失、主窗口隐藏/最小化、用户退出接管、切换设备/模式、画面停滞、输入过载、系统休眠通知、串口错误或退出应用，均触发同一释放路径。

Serial 线程独立检查 UI 心跳；接管期间主线程超过 250 ms 未更新心跳，即清除旧队列并尽力释放。该机制覆盖 UI/渲染卡住但串口线程仍运行的情况，不覆盖整个进程崩溃或物理断线。

**没有仍可通信的链路，就无法保证把“松开”送到目标。** 串口被拔掉而 CH9329 仍然供电时，目标可能保留按住状态；界面必须诚实报告释放未确认，并提示必要时重新插拔被控端 HID。不要用软件 watchdog 的存在声称已经解决全部硬件失联情形。

## 10. 生命周期与异常恢复

视频状态和控制状态独立。视频预览可以在串口未连接时运行；控制接管必须同时满足新鲜视频、有效串口、目标 USB ready 和已完成清零。

视频自动重连只针对同一强匹配设备，退避为 0.5、1、2、5 秒，之后保持 5 秒。弱匹配或多个候选必须用户确认。串口重新出现后可尝试恢复连接，但控制始终回到 Preview，不自动恢复此前按下的键或鼠标按钮。

用户选择切换设备/模式时，先退出控制，再异步停止旧源、提高 generation、清空样本和帧 mailbox，最后启动新源。主线程显示 Connecting/Stopping 状态，不同步卡住等待。

关闭顺序为：停止接受输入并请求清零；停止采集和所有回调发布；唤醒并结束 Video 线程；等串口完成有界释放/关闭；确认没有后台线程再访问资源；在主线程销毁视频纹理、ImGui、GL context 和 SDL 窗口；最后保存配置与关闭日志。

原生驱动 API 不保证所有系统故障都能在固定时间返回。本应用应确保自己的等待可取消，关闭超过 2 秒要保持“正在停止”的可见状态；不使用 TerminateThread、不分离仍持有对象的线程，也不在回调存活时强行释放其 context。卡死驱动不纳入“任何情况下 2 秒退出”的不实保证。

## 11. UI、配置与诊断

主界面只保留一条设备/模式工具栏、一块视频区域和状态栏。只创建一个 SDL 窗口，不开启 ImGui multi-viewport，也不在首版增加可停靠的多窗口工作区。连接设置包含采集设备、采集模式、串口、波特率和连接按钮；控制设置包含鼠标模式、Host key、灵敏度、VSync 和颜色覆盖。

采集状态、串口状态、目标 USB 状态和控制接管状态分别显示，不能合成一个意义不清的绿色“已连接”。全屏使用无边框全屏，不为了进入全屏修改控制端显示器分辨率。

配置使用一个带 schema_version 的 JSON 文件，放在 SDL_GetPrefPath 得到的用户目录。只保存设备标识、用户选项和窗口参数；临时连接状态、按住状态、队列内容不保存。保存采用同目录临时文件加原子替换；格式损坏时备份后使用默认值。没有数据库、配置同步和自动更新器。

诊断面板显示实际采集模式、采集/解码/呈现新帧率、两个 mailbox 的覆盖计数、帧到达至提交耗时、输入排队时间、串口 ACK RTT、超时数、当前像素处理路径及最近的错误。

统计使用单调时钟、固定容量滑动窗口；捕获序号去重后才计算呈现帧率。30 fps 视频以 120 Hz 重画同一纹理，不能报告为 120 fps 视频。设备 PTS 和控制端时钟未对齐时，不直接相减生成“端到端延迟”。

普通日志总量轮转为 3×10 MiB，默认记录状态变化和聚合指标，不记录输入文本、逐键轨迹、截图或视频。采集回调内禁止同步刷文件。串口调试包记录需显式打开并提示其可能暴露输入内容。

## 12. 未来串流的接入点

只保留已在首版使用的两个数据边界：VideoFrame 和 ControlEvent，不实现空的网络模块。

未来控制端窗口可从网络解码器接收 VideoFrame，继续使用现有 Renderer；InputRouter 仍生成相同 ControlEvent，由新的 NetworkControlSink 发送。远端采集节点复用 CaptureSource、VideoProcessor 和 Ch9329ControlSink。

视频编码器从显示之前的 VideoFrame 获取数据，不录制包含 ImGui 的窗口，不做 GPU 截图回读。编码分支拥有自己的有界队列，网络拥塞不能反向阻塞本地采集和预览。

键盘/按钮/reset 需要有序可靠语义。将来设计网络协议时必须增加控制权、会话 epoch、超时释放和身份认证/加密；鼠标运动能否采用不可靠传输要与按钮边界一起设计，不能简单把所有鼠标包丢到 UDP。

现阶段不选择 WebRTC、QUIC 或其他传输协议，不引入编码器依赖，不写远程服务。不要直接暴露一条“网络透传 CH9329 串口字节流”作为最终架构，因为它无法自然表达会话失效、重复相对移动和控制权释放。

## 13. 仓库组织与构建

采用一个仓库、一个应用进程、一个可独立测试的内部静态库。目录按功能划分，而非创建一套层层嵌套的 framework。

| 路径 | 内容 |
|---|---|
| `src/app/` | Application、KvmSession、主循环、窗口状态。 |
| `src/ui/` | 主界面和诊断面板，不放业务协议。 |
| `src/video/` | CaptureSample、VideoFrame、VideoProcessor、两个 latest mailbox。 |
| `src/video/capture/` | capture_source.hpp、capture_mf.cpp、capture_v4l2.cpp、capture_avfoundation.mm。 |
| `src/render/` | VideoRenderer、GL 资源封装、有限的 YUV 转换 shaders。 |
| `src/input/` | ControlEvent、InputRouter、坐标映射和物理键码映射。 |
| `src/control/` | ControlSink、CH9329 codec/parser、HID 状态、输入队列和串口 worker。 |
| `src/support/` | 配置、日志和固定容量指标统计。 |
| `tests/` | 协议、输入、队列、视频所有权、生命周期和故障注入测试。 |
| `packaging/` | Windows、Linux 和 macOS 的资源、打包和签名配置。 |
| `docs/` | 本规格、硬件验收记录、构建方法和故障排查。 |

提供 Debug、Release 和支持平台的 sanitizer CMake presets，所有测试通过 CTest 调用。平台判断集中在构建文件和平台适配器内，不在业务代码中散布大量条件编译。

依赖在首个构建任务中锁定到实际验证过的发布 tag/commit 和 vcpkg baseline；禁止跟随 master/latest。ImGui 核心与后端必须来自同一个版本。记录 FFmpeg 版本、配置参数和是否启用 GPL/nonfree 组件。

首版仅构建所需 FFmpeg 功能，不因为未来串流提前引入 x264/x265 等编码依赖。FFmpeg 和 libserialport 采用动态链接，随发布包提供实际分发版本的许可证、对应源码获取方式、修改和构建信息；动态链接本身并不代替许可证合规工作。[S11][S14]

Windows 输出可解压运行的目录，随附 DLL；Linux 先提供针对验收发行版的可运行目录与安装说明，不把 AppImage/Flatpak 再变成一项首版工程；macOS 输出标准 `.app`，处理库路径、摄像头说明和分发所需的签名/权限配置。没有签名凭据时交付可本地构建测试的包，并明确标识未签名，不能声称已完成公证。

## 14. Implementation Plan

以下是交给 coding agent 的实施顺序。负责人名称只是任务分工，不表示这些工作已经执行。单一 coding agent 可以依次承担全部角色；多人并行只允许在已固定的数据合同两侧开展。

每个任务都先建立本节列出的可失败测试或可重复实机检查，再实现最小闭环。任务完成时提交其代码、测试和相关操作说明，不把测试全部拖到项目结尾。

### P0：构建与硬件接入核验——平台负责人 Atlas

产出三平台 CMake 工程、依赖锁定、最小 SDL3/ImGui/OpenGL 窗口，以及仅供开发使用的设备能力与串口握手诊断入口。工作涉及构建文件、`src/app/`、`src/video/capture/` 的枚举部分和 `docs/hardware-validation.md`。

必须取得采集卡的实际设备标识、模式列表、可稳定交付帧率；取得所选串口的 GET_INFO 应答、目标 USB 状态、当前波特率，以及有硬件依据的供电/高速串口配置。记录实际机器、系统、驱动、USB 连接方式和板卡配置，不用芯片名称替代这些信息。

检查三平台窗口均可启动；检查非 ASCII 设备名称；检查设备不存在、权限被拒和端口被占用时不会崩溃。没有目标硬件时允许用假设备继续软件任务，但实机核验必须明确未完成。

### P1：协议与控制状态——控制负责人 Relay

实现 `src/control/` 中的纯协议 codec/parser、HID 状态、队列和串口 worker，以及 `tests/ch9329_*`、`tests/control_queue_*`。

先建立正常包、坏校验、逐字节输入、粘包、LEN 超限、部分写入、错误 ACK、迟到 ACK 和超时的测试；再完成串口握手与释放。重点证明 Ctrl 按住后失联不会在重连时被恢复，滚轮和相对移动不会因 ACK 丢失重复发送。

完成条件是无 UI 情况下能通过假串口完整测试，并在真实 CH9329 上演示受控按下/释放和目标 USB 断开状态；不以“能向串口 write”作为完成。

### P2：持续新鲜的视频闭环——视频负责人 Photon

实现 CaptureSource 三个平台适配器、LatestSample、VideoProcessor、LatestFrame 和 VideoRenderer，对应 `src/video/`、`src/render/` 与视频测试。

先用带 frame sequence 和时间戳的假源建立“消费者变慢时不补播历史”的测试，再接入 Raw/MJPEG。按 Raw 预览、MJPEG 解码、颜色/stride、三平台启动停止的顺序完成。

完成条件是支持的 1080p60 模式下能够持续显示、主线程短暂停顿后恢复最新画面，并且连续 100 次打开/关闭没有死锁、悬空访问或持续增长的持有帧。

### P3：可用的 KVM 交互——输入负责人 Keystream

实现 InputRouter、接管状态机、物理键码、两种鼠标模式、特殊按键和全屏 UI。工作涉及 `src/input/`、`src/ui/` 和输入路由测试。

先测试首次点击只接管、Host key 不外泄、接管前已按住键被隔离、画面黑边不点击、拖出后的 button-up 仍发送、快速按键保留边沿，再接入 SDL 实际事件。不能用帧末一次 GetKeyboardState 快照替代事件流。

完成条件是在真实桌面完成输入文字、快捷键、拖动、滚轮、目标输入法操作和全屏切换；在至少一台 UEFI/BIOS 上完成键盘操作，并记录其鼠标模式兼容性，不宣称所有固件均已兼容。

### P4：会话恢复与诊断——集成负责人 Atlas

完成 KvmSession、配置、状态区分、画面停滞、UI 心跳、设备重连、模式切换和有序关闭。测试覆盖采集卡拔插、串口拔插、目标 USB 拔插、最小化、焦点丢失、睡眠恢复，以及持键期间发生这些事件。

完成条件是恢复后回到 Preview，没有旧输入重放；设备列表重新排序不切到其他设备；最后一帧停滞时界面明确告警；诊断里的帧率和时钟含义正确。

### P5：发布与客观验收——测试负责人 Sentinel

执行下一节全部验收项，记录三平台证据、硬件延迟数据和已知限制，完成 release 打包、第三方声明及构建文档。工作涉及 `tests/`、`packaging/`、CI 和 `docs/acceptance.md`。

软件测试失败、关键生命周期不稳定或某平台只编译未实测，不能用新增功能弥补。通过首版后再立网络串流的独立设计任务，不在 P5 顺带加入编码器或远程服务器。

## 15. 验收规格

### 15.1 自动化正确性测试

| 测试对象 | 必须覆盖的判据 |
|---|---|
| 协议编解码 | 官方命令示例作为基础向量；另加入非零地址、边界坐标、负位移、非零 modifier 的独立计算向量；随机分片、噪声和校验损坏均不得越界。 |
| 键盘 | 左右 modifier、六键限制、第七键忽略规则、重复事件、快速 tap、按住退出、重新进入时物理键隔离均符合本规格。 |
| 输入队列 | 运动只在相邻且无边界时合并；按键/按钮顺序保留；ReleaseAll 在满队列时仍可触发；旧 epoch 全部丢弃。 |
| 坐标 | 16:9、4:3、超宽窗口和不同 HiDPI 比例下，真实视频矩形一致；四角输出范围正确；黑边点击被拒；拖出后的释放送达。 |
| 相对运动 | 正负、小数和大增量拆分后总量守恒；不会把截断余量丢掉；模式切换不带入旧增量。 |
| 视频 | Raw/MJPEG、常见 YUV 平面布局、padding stride、上下翻转、有限/全范围；新 generation 后不呈现旧帧。 |
| 生命周期 | 假回调晚到、设备无帧、停止期间仍有回调、格式变化、消费者停顿，都不会 use-after-free 或无限等待应用自己的队列。 |
| 串口故障 | partial write、延迟/丢失/畸形 ACK、断线和重连不会导致重复相对移动、重复滚轮或旧按键重放。 |

纯软件测试在三平台 CI 上运行。Linux 增加 ASan/UBSan；并发测试在支持环境运行 TSan。CI 通过不代替 UVC、CH9329 和窗口系统的实机测试。

### 15.2 性能目标和测量口径

在确认能稳定交付 1080p60 的采集模式和性能足够的参考主机上测量。性能报告必须给出原始格式、分辨率、实际帧率、串口速率及系统环境。

| 指标 | 首版目标或判据 |
|---|---|
| 样本到达至 GPU 提交 | 60 fps 参考环境下 p95 ≤ 20 ms；起点为采集回调进入/成功 DQBUF，终点为本帧绘制提交。它不包含 HDMI 采集卡内部延迟，也不是显示器真正发光时刻。 |
| 输入出队至首次串口写入 | 无在途拥堵、57600/115200 参考配置下，键盘和按钮边沿 p95 ≤ 5 ms；纯运动另受最多一个合并周期影响。 |
| 输入事件总排队 | 必须记录；超过 100 ms 触发失效释放，不能继续积压。 |
| 正常释放 | 健康链路的参考环境下，触发后 50 ms 内完成所需释放应答为目标；异常 ACK/断线场景必须显示未确认，不能伪报完成。 |
| UI 失去活性 | Serial 线程在 UI 心跳过期 250 ms 后停止接收旧会话输入并启动释放；该检查不依赖渲染线程执行。 |
| 过载恢复 | 让显示或解码消费者停顿 500 ms，恢复后消费最新候选，不把积压历史逐帧补播；UI 停顿同时应触发控制退出。 |
| 长时间运行 | 持续 1 小时、执行 100 次连接/断开；无死锁、崩溃或持续线性内存增长，记录稳定态 RSS 与帧持有数量。 |

输入延迟起点还需分别记录 SDL 事件时间和应用实际出队时间；只报告出队之后的 5 ms 不能掩盖主线程已经卡住 100 ms。ACK RTT 单独记录，它不是目标应用响应时间。

端到端视频延迟用外部高速摄影比较同一被控画面在参考显示器与 KVM 窗口上的变化，至少采集 100 次变化。争取参考硬件下中位数 ≤ 80 ms、p95 ≤ 120 ms，但这些是系统级优化目标，受采集卡和显示链路影响，不能仅由应用内部时间戳宣称达成。

对未达标项先区分采集卡内部、驱动排队、拷贝/解码、显示合成、串口 RTT 和目标系统响应，再决定修改哪个环节。不得仅为了提高 FPS 而引入额外缓冲。

### 15.3 实机交互清单

三个控制端平台均需实际连接采集卡和 CH9329，完成桌面点击定位、拖动越界、滚轮、长按、快速输入、左右修饰键、目标锁屏/登录界面、接管释放、全屏、目标输入法及设备断开恢复。

Linux X11 与 Wayland 分别验证输入捕获和系统快捷键限制；macOS 验证首次授权、拒绝授权和恢复权限；Windows 验证设备繁忙及常见系统保留组合键。未获系统许可的快捷键必须通过菜单可发送，或者明确列出限制，不能声称“所有键均可截获”。

验收报告最后分别列出已通过的软件测试、已验证的真实硬件组合、实测性能和未验证项。没有硬件测量就写未测，不用模拟源数据冒充实际 KVM 性能。

## 16. 实现禁止项与完成定义

禁止把视频做成按 PTS 排队的播放器；禁止每帧全量 CPU RGB 转换作为常规路径；禁止让 UI 等待串口；禁止用无界队列隐藏处理能力不足；禁止把按键边沿合并成每帧最后状态；禁止 ACK 超时后重发相对移动；禁止设备重连后恢复旧按住状态；禁止为了将来串流加入当前没有消费者的网络/插件框架。

Coding agent 的交付应包含可构建源代码、依赖锁定、测试、三平台打包配置、用户操作说明、硬件验收记录和已知限制。实施应按 P0—P5 推进；本地 KVM 闭环通过验收才算首版完成。

本设计选择保留一次受控采集拷贝、四个职责清楚的线程、两个视频单槽和一个有序输入队列。优化目标是最新画面、及时且语义正确的输入、可解释的异常状态，而不是代码层面的“零拷贝”“全异步”或抽象数量。
