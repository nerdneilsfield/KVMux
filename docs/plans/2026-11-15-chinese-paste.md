# 中文粘贴：Unicode 十六进制与五笔

推荐主路径是 Windows 上的 Unicode 十六进制码点按键。五笔保留为后备，不进入第一段实现。

选十六进制，是因为它不携带码表，仓库不必纳入许可证互相冲突的五笔数据。英文仍走现有 ASCII 引擎，汉字按码点发送，段落之间不发送中/英切换键。

风险：启用步骤来自微软问答和厂商文档，本轮没有找到产品注册表参考页。按住 Alt 再按 A 至 F，可能打开菜单；纯数字码点在 Word 里曾被按十进制解释。中文输入法是否截获该序列、基本多文种平面（BMP）以外的码点、记事本以外的控件，以及 CH9329 是否接受小键盘用法，都没有真机记录。macOS 与 Linux 各用自己的按键序列。

提交 `d9ee8aa830e46bc96025b7553d88c607cf5553d3` 仍把范围内的中文引擎写成五笔。采纳本文需要另一次范围修订。本文不改 `AGENTS.md`，也不改 `docs/design/kvm-technical-design-v1.md`。

证据分三类。读到的事实是本轮打开的代码、设计文档或网页原文。推测是由这些事实推出、尚未测量的判断。未验证是必须在目标机上另行记录的行为。

## 安全约束

两条路径都沿用现有 ASCII 粘贴的约束：

- 只有用户明确开始后才发送。
- 事件经过现有 `InputRouter` 和 `ControlSink`，有节奏、有长度上限。
- 取消、超时、过载、画面过期、失焦、设备变化、睡眠和退出都走公共释放路径。
- 不把剪贴板原文、五笔编码或十六进制字符串写入日志、配置或磁盘。
- 不把 SDL 文本输入当成远端按键。Host 键只留在本机，两条路径都不发送它。

链路丢失之后，释放不得报成已确认。旧控制代次不得重放。

## 两条路径

| 问题 | 十六进制路径 | 五笔路径 |
| --- | --- | --- |
| 目标机前提 | 当前用户已启用 `EnableHexNumpad` 并重新登录；NumLock 打开；输入法放行 ASCII 用法和 Alt 序列 | 用户已装好并选中一份五笔；86 或 98、简码、重码、上屏和标点都按一份写死的配置工作 |
| 中英混合 | 英文走 ASCII，汉字走码点。不发送切换键。输入法若正处于中文模式，英文仍可能被吃掉 | 中文段和英文段要处于相反模式。程序读不到当前模式，切换键会和真实状态错位 |
| 码表 | 不需要 | 本轮没有确认可以放进 MIT 树的单字表 |
| 一字的按键 | 左 Alt 按下，小键盘 `+`，十六进制各位，松开 Alt | 一至四码，再加可能的上屏键或候选序号 |
| 失败时程序能否发现 | 不能。菜单被打开、输入法截获、字符不对，链路上看都是 ACK 成功 | 不能。上屏错字、停在预编辑，链路上看也都是 ACK 成功 |
| 第一段实现 | 建议先做，但记事本手工验证失败就不做 | 留到有可分发码表、并且十六进制验证失败之后 |

主路径先做 Windows。macOS 的 Unicode Hex Input 和 Linux 的 Ctrl+Shift+U 是另一套按键，不放进第一段。

## Windows 十六进制

### 启用

本轮检索 `learn.microsoft.com`，没有找到把 `EnableHexNumpad` 写成注册表参考的产品页。读到的是问答和一份厂商手册：

- 微软问答 2010-05-24 被采纳的回答写：检索 `EnableHexNumpad`，可以看到微软准备过一套 Unicode 输入，但默认不启用，回答者猜测是因为这些按键经常会激活菜单。同一回答写明，大于 255 的十进制小键盘码除 Word 和写字板外一直回绕。
- 微软问答繁体中文帖，回答时间 2016-10-10：在 `HKEY_CURRENT_USER\Control Panel\Input Method` 下新增字符串 `EnableHexNumpad`，数值数据 `1`；注销后重新登录；按住左边的 Alt，按九宫格里的 `+`，再输入码。
- 微软问答 2023-11-06 的 Windows 11 回答（论坛用户，不是微软员工）：同一路径、字符串、数值 `1`，然后重启。
- Zebra RS6100 产品参考把同一项写成 `REG_SZ`，并要求重启。这是厂商手册，不是微软文档。

类型按这些原文取 `REG_SZ`，数值为 `1`。重新登录还是重启，几份原文不一致。手工验证先注销再登录；若序列仍无效果，再重启。KVMux 不改目标机注册表。

按键顺序按繁体中文问答和 Super User 上转引的操作说明：按住左 Alt，按小键盘 `+`，输入十六进制，松开 Alt。0 至 9 用小键盘，A 至 F 用主键盘字母。不按 Shift。

### 码点范围

已打开的微软页面没有写接受的码点上限，也没有写 BMP 以外要不要拆成 UTF-16 代理对。推测：松开 Alt 时，已经按下的十六进制就是码点，不补前导零。`U+4E2D` 发 `4e2d`，`U+1F600` 发 `1f600`。代理项 `U+D800` 至 `U+DFFF` 不是标量，函数直接拒绝，不发两段代理。

这一猜测要由手工验证判定。若一个标量的十六进制在记事本里得不到该字符，再考虑代理对；在那之前不为 Windows 实现代理对。

### NumLock

`Ch9329ControlSink` 的 `GET_INFO` 把应答 `data[2]` 的 bit 0 记成 `num_lock`，bit 1 为 Caps Lock，bit 2 为 Scroll Lock，并放进 `keyboard_leds`（`src/control/serial_worker.cpp`）。设计文档要求空闲时查询 `GET_INFO`，间隔不少于 1 秒，交互期间不用状态轮询抢占发送。

本轮打开的微软问答没有写十六进制序列是否依赖 NumLock。有 Super User 回答转引维基百科：有的 Windows 版本要求 0 至 9 打在小键盘上，或要求 NumLock 打开。维基原文本轮没有打开。

默认：最近一次 `GET_INFO` 看不到 NumLock 点亮时，拒绝开始十六进制粘贴，不向目标机发送 NumLock 切换。LED 尚未读到时同样拒绝。这只能说明探测那一刻芯片报告的灯状态。灯在探测之后被用户改掉，程序不会知道。芯片是否如实转发 Windows 的灯，未验证。

### 字母键和菜单

A 至 F 对应 USB HID usage `0x04` 至 `0x09`，也就是 US QWERTY 上 A 至 F 的物理位置。KVMux 发送的是用法，不是字符。目标机若不是 QWERTY，Windows 未必把 `0x04` 当成十六进制的 A。中文 Windows 常见键盘是 QWERTY。非 QWERTY 未验证。

按住 Alt 时，主键盘字母同时是菜单加速键。记事本里 Alt+F 是文件菜单，Alt+E 是编辑菜单。`U+4E2D`（中）的十六进制是 `4e2d`，中间有 E 和 D。`U+7684`（的）是 `7684`，四位都是数字。

2024 年一条 Reddit 提问说，记事本里用小键盘 `+` 加 `A9` 能得到 `U+00A9`，并询问 `U+1F419` 里的 F 会不会撞上文件菜单。帖子正文本轮没有取回，不能当成失败记录。2010 年问答把“经常激活菜单”写成默认不启用的猜测，也不是测量。

Super User 2021 年的帖子报告了另一类偏差：Word 里 `Alt` 加小键盘 `+` 再输入 `1200`，得到的是十进制 1200 对应的 `U+04B0`；同一帖写，一旦序列里出现 `a` 至 `f`，Word 才按十六进制解释。这是用户实测报告，不是微软规格。若该行为成立，全数字的“的”在 Word 里会错，含字母的“中”反而可能对。记事本则可能相反。

所以手工验证必须两个字都做，不能只试一个。

### 输入法

KVMux 读不到目标机输入法处于中文还是英文。两种模式下 Alt 序列会不会被截走，已打开的资料没有写。这项未验证。

十六进制路径不在中英文之间发送切换键。它仍然要求整段粘贴期间，输入法对 ASCII 用法和这条 Alt 序列都按物理键放行。输入法若正处于中文模式，现有 ASCII 路径的字母也会变成编码，英文段一样会错。这个错法程序看不到。

### 不同控件

Word 那一格引用了社区报告。其余格子没有 KVMux 的真机记录。Rich Edit 的 Alt+X 是另一套机制，不填进 `EnableHexNumpad` 的结果。

| 控件 | 本轮能写的 | 状态 |
| --- | --- | --- |
| 记事本 | 社区帖讨论过 `U+00A9` 和菜单键冲突，没有 KVMux 记录 | 未验证 |
| Win32 编辑框 | 没有打开的原文 | 未验证 |
| 浏览器地址栏和网页输入框 | 没有打开的原文 | 未验证 |
| Windows Terminal、conhost | 没有打开的原文 | 未验证 |
| 远程桌面 | 没有打开的原文 | 未验证 |
| UAC、密码框 | 没有打开的原文。这类界面经常不走普通输入法 | 未验证 |
| Word | Super User 2021 报告纯数字序列被当成十进制 | 社区报告，目标机未验证 |
| Rich Edit | 见下一节，不是 `EnableHexNumpad` | 官方页只描述本控件 |

同一键盘上的 Alt 和小键盘是否必须来自同一 HID 设备，本轮没有核对到微软原文。CH9329 在目标机上只呈现一个键盘，拓扑上是同一设备。Windows 是否另外检查设备身份，未验证。

松开 Alt 之后菜单栏被激活、字符却没有插入，是这条路径最需要排除的副作用。取消粘贴时公共释放会再发一次修饰键全 0 的报告；若此时菜单已经打开，这次释放不会把菜单关掉。未验证。

## 十进制 Alt 码为什么不够

不改注册表时，按住 Alt 再在小键盘上输入十进制，走的是当前 256 字符集。2010 年被采纳的问答写：至少从 Windows 3.1 起就是这样；数值大于 255 时一直回绕；Word 和写字板后来才对大于 255 的十进制插入 Unicode，而且只在这两个程序里。

汉字不在一张 256 字符的代码页里。回绕之后也不是该汉字的码点。因此十进制 Alt 码不能当作中文粘贴。

`learn.microsoft.com` 的 HexToUnicode IME 页写的是 Rich Edit 3.0：先打出十六进制，再按 Alt+X；或在该控件里用 Alt+小键盘输入大于 255 的十进制。页内没有 `EnableHexNumpad`。Alt+X 在有的程序里还是退出。这不是系统级路径，覆盖不了记事本、终端和密码框。

## macOS 与 Linux

这两节不是 Windows 主路径的等价物。真机行为未验证。

macOS 要先把 Unicode Hex Input 加进输入源并切到它。Ask Different 的回答写：按住 Option，BMP 字符打四位十六进制；超过四位时，系统只吃前四位。同一回答给的办法是打 UTF-16 的八位十六进制，例如 `U+1D11E` 打 `d834dd1e`。一份操作说明写，八位序列的前四位之后可能先出现一个中间字符。Apple 社区帖称，四位码点以 0 开头且以 0 结尾时，在 macOS 12.4 至 13.2.1 上失败，并称苹果支持的测试确认过；这是论坛转述，不是苹果工程说明。Option 在苹果键盘上通常是左 Alt，usage `0xE2`。目标机没切到这个输入源时，同一串按键不会产生码点。

Linux 以 ArchWiki IBus 页（本文取回时的版本 `oldid=878551`）为准：按 Ctrl+Shift+U，出现带下划线的 `u`，再输入码，按 Space 或 Enter 提交。X11 下该页要求 `GTK_IM_MODULE=ibus`、`QT_IM_MODULE=ibus`、`XMODIFIERS=@im=ibus`。Wayland 下 GTK 与 Qt 的变量不同。不用 IBus 的程序、把这个组合键留给自己的终端，都不能假定会提交。GTK 简单输入上下文是否另外写死同一序列，本轮没有打开 GTK 源码。Fcitx5 手册本轮没有打开，不把 Ctrl+Shift+U 写成 Fcitx5 的事实。

Ctrl 是 usage `0xE0`，Shift 是 `0xE1`。这和 Windows 的左 Alt 加小键盘不是同一串边沿。第一段不为 Linux 或 macOS 各写一个引擎。

## CH9329 与 Alt 残留

`supported_usb_keyboard_usage` 接受 `0x04` 至 `0x73`（`src/input/input_router.cpp`）。小键盘 `+` 是 `0x57`，小键盘 1 至 9 是 `0x59` 至 `0x61`，小键盘 0 是 `0x62`，小键盘小数点是 `0x63`。字母 A 至 F 是 `0x04` 至 `0x09`。这些用法都落在已接受范围内。协议帧头 `kHeader0` 也是 `0x57`（`src/control/ch9329_protocol.hpp`），那是帧字节，不是小键盘 `+`。

`HidKeyboardState` 把 `0xE0` 至 `0xE7` 放进修饰字节，不占六个普通键槽。左 Alt 是 `0xE2`。按住左 Alt 再按下其中一个普通键，占用一个槽。十六进制序列每次只按下一个普通键，然后松开，不同时按下两个普通键，因此六键滚转不会把某一位丢进 `ignored_`。

`U+4E2D` 的边沿是 12 帧：左 Alt 按下，小键盘 `+` 按下并松开，`4`、`e`、`2`、`d` 各按下并松开，左 Alt 松开。数字用小键盘，不用主键盘数字行。

软件侧保证 Alt 会松开的路径是现有公共释放，不是新的队列：

- 进行中的粘贴被 `cancel_ascii_paste` 取消时，会 `request_release`，把 `release_confirmed` 清掉，并置 `release_requested`。
- `release_all` 同样取消粘贴并 `request_release`。
- `release_requested` 之后 `begin_clear` 调用 `keyboard.clear()`，修饰字节变为 0，再发送六个用法全 0 的键盘报告。
- 已经写进串口、尚未收到 ACK 的那一帧仍要等应答；注释写明不能把已写出的报告截断。应答之后才进入清除。
- `fail` 也会 `keyboard.clear()`。链路已经断开时，清除报告发不出去，释放保持未确认。

这保证的是本进程发出的下一帧不再带 Alt。它不保证目标机已经处理 Alt 抬起。清除帧超时或断线时，界面不得显示释放已确认。目标机上是否还留着 Alt 菜单，未验证。

固件是否把 `0x57` 和 `0x59` 至 `0x62` 原样交给 Windows，未验证。InputRouter 接受这些用法，只说明主机侧不会在入队前丢掉它们。

## 速度

设计文档写明不为每个输入报告硬编码 20 ms 或 50 ms 的 sleep。诊断用最小帧间隔默认是 0，下一帧在上一帧 ACK 之后就发。115200 下约 20 字节的一帧，仅串行时间约 1.74 ms，还不包含 USB 和芯片。`kStallTimeout` 是 100 ms，`kHardTimeout` 是 500 ms。

下面的 25 ms/帧是规划估算，不是源码里的常数，也不是已测量的 CH9329 间隔。一个普通键是按下、松开两帧。修饰键的按下或松开各是一帧。

| 一个字 | 帧数 | 按 25 ms/帧 | 1000 字 |
| --- | --- | --- | --- |
| 四位十六进制，例如“中”“的” | 12 | 300 ms | 300 s |
| 五位，例如 `U+1F600` | 14 | 350 ms | 350 s |
| 五笔四码且第四码自动上屏 | 8 | 200 ms | 200 s |
| 五笔四码再加一次上屏键 | 10 | 250 ms | 250 s |

五笔一行是推测：很多字不是四码，重码还要候选序号，词组和联想会把若干字合成一次上屏。Rime `wubi86.schema.yaml` 里 `max_code_length: 4` 被注释掉，不能把“四码唯一即上屏”写成这份方案的事实。实际耗时由 ACK 往返决定。内部时间戳不能写成 KVM 性能。

ASCII 段更短。一个不带 Shift 的英文字母是两帧。中英混合时，只有非 ASCII 标量走 12 帧那一档。

## 中英混合

分段规则：

1. 把剪贴板按 UTF-8 解成标量。非法 UTF-8、代理项、大于 `U+10FFFF` 的值，整段拒绝。标量数超过 65536 时也整段拒绝，与现有 ASCII 粘贴的长度上限一致。
2. 现有 ASCII 引擎已经接受的标量，包括可打印 US-ASCII、Tab 和换行，仍调用那条映射。用法和 Shift 规则不另写一套。
3. 其余标量走十六进制边沿。函数不接受 ASCII 区，避免两个函数都能发同一个字。
4. 两段边沿接在同一次粘贴作业里，按顺序发送。中间不插入切换输入法的键。

不能自动发现的失败：

- 注册表未设置，或改完没有重新登录。`GET_INFO` 读不到这项。
- 输入法处于中文模式，字母变成编码，或 Alt 序列被预编辑吃掉。
- 焦点所在控件不用这套十六进制，或把 Alt+字母当成菜单。
- 目标布局不是 QWERTY，A 至 F 的用法对不上十六进制字母。
- NumLock 在最近一次 `GET_INFO` 之后被关掉。
- BMP 以外的标量只发一段十六进制时，系统截断或忽略这段输入。

这些情况下串口 ACK 仍然可以成功。进度只能表示帧已发出，不能表示屏幕上出现了预期字符。

## 码表与许可证

十六进制路径不把码表放进仓库，也不把码表链进二进制。MIT 树因此不必处理五笔数据的再分发条件。这是它相对五笔的许可证好处。

五笔后备若要随程序分发码表，本轮读到的材料不够：

- `rime/rime-wubi` 仓库根上的 `LICENSE` 是 GNU LGPL 3.0，日期 2007-06-29。`wubi86.schema.yaml` 的 `schema_id` 为 `wubi86`，版本 `0.21`，说明写“码表源自 ibus-table”。开关包括 `ascii_mode`（中文/西文，`reset: 0`）、全角、常用/增广、中英文标点。翻译器打开了 `enable_sentence`，`max_phrase_length` 为 4。这是词组表，不是一字一码。把 yaml 嵌进 MIT 二进制算不算 LGPL 的 Combined Work，是推测，本计划不靠这个推测来分发。
- `fcitx/fcitx5-table-extra` 的 README 写代码为 GPL-3.0 或更新版本，并写“All the data file is now in public domain.” `tables/` 里有 `wubi-large.txt`。该文件开头是 fcitx 码表头，没有单独的许可证行；内容含简码（`a` 对应“工”）和词组。public domain 只出现在 README 的一句里，没有落到这个文件上。本轮也没有找到王永民或这份表可以随 MIT 工程再分发的授权，因此不把 `wubi-large.txt` 放进仓库。
- 极点、海峰、搜狗、QQ 或微软五笔自带的表，本轮没有取到可以随 MIT 工程再分发的许可证正文。未确认的来源不用。
- Rime 用户词库含有使用者自己的词，任何路径都不打包、不上传。

所以五笔不是“先实现、码表以后再说”。没有一份可以携带的单字表时，后备也只停留在本文。

## 五笔后备的前提

五笔不是一字一固定码。同一编码可以对应多个字（重码），一个字也可以只有一至三码（简码）。第四码是否自动上屏、候选顺序、调频、联想、全角标点，都是目标机上那一份输入法的设置。86 与 98 的编码不一样。KVMux 读不到这些开关。

本轮没有逐家核对微软五笔、搜狗、QQ、macOS 自带五笔、fcitx5 和 ibus 的手册。不能在文档里写死哪一个快捷键是中/英切换。Rime 那份 schema 只说明该文件自己的开关名。

若以后实现五笔，开始之前由用户声明三件事，程序不探测：

1. 输入法名称和版本，以及 86 还是 98。
2. 开始时已经处于中文模式。
3. 四码上屏、简码、重码时用哪一个序号键、标点是全角还是半角。声明与目标机不一致时，错字无法从 ACK 看出来。

英文段仍走 ASCII 引擎。中文段与英文段之间若必须切换模式，切换键属于这份声明的一部分，并且任何取消都要走公共释放。声明错了，切换会把模式越切越偏。这也是十六进制被放在前面的原因。

## 无法覆盖时

十六进制函数拒绝：非法 UTF-8、代理项、大于 `U+10FFFF`、非字符（`U+FDD0` 至 `U+FDEF`，以及每个平面末尾的 `FFFE` 和 `FFFF`）、C0/C1 控制符。Tab 和换行不进这个函数，由 ASCII 路径处理。表情符号是标量，不因“表里没有”而拒绝。目标机是否显示该符号，未验证。

五笔路径上，表里没有的字、表情和控制符同样整段拒绝。不静默跳过。跳过会让后面的字仍然发出去，用户看到的是缺了一段的句子，程序却可能报完成。

拒绝时界面给出原因类别和被拒标量的个数，不写出原文、码点或编码。日志同样不写。

## 分层

纯函数做两件事，都可以离线测：

- 标量到十六进制边沿。输入是一个码点，输出是 `(usage, pressed)` 序列，或一个错误。
- 若做五笔，另一个纯函数把一个字映射成编码和候选序号。期望值来自外部表，不来自函数自己的查表结果回写。

分段、作业、节奏和取消不放进纯函数。它们复用现有 ASCII 粘贴作业：一次作业、一串边沿、串口线程一帧一帧等 ACK。不另开队列，不为每个码点起任务。现有 API 的名字带 ascii。实现时可以沿用这个作业，或给同一作业一个更宽的名字。无论名字如何，取消仍进 `cancel_paste_locked` 和 `request_release`。

UI 不在等待串口。开始之后只显示已完成边沿数。不把剪贴板留在界面状态里超过这次作业的生存期。

## 验证

### 纯函数

CTest 的期望值写死在测试里，按 USB HID 用法表人工列出，不调用被测函数来生成期望。

`U+4E2D` 的期望边沿：

| 顺序 | usage | 按下 |
| --- | --- | --- |
| 1 | `0xE2` 左 Alt | 是 |
| 2 | `0x57` 小键盘 `+` | 是 |
| 3 | `0x57` | 否 |
| 4 | `0x5C` 小键盘 4 | 是 |
| 5 | `0x5C` | 否 |
| 6 | `0x08` 字母 E | 是 |
| 7 | `0x08` | 否 |
| 8 | `0x5A` 小键盘 2 | 是 |
| 9 | `0x5A` | 否 |
| 10 | `0x07` 字母 D | 是 |
| 11 | `0x07` | 否 |
| 12 | `0xE2` | 否 |

`U+7684` 把第 4 至 11 步换成小键盘 7、6、8、4，用法是 `0x5F`、`0x5E`、`0x60`、`0x5C`，各有按下和松开。Alt 与小键盘 `+` 的前后帧不变。

另外断言：`U+1F600` 发出 `1f600` 五位，不拆代理；`U+D800`、`U+000A`、`U+110000` 拒绝且不产生边沿；序列中不同时按下两个普通键；Host 用法不出现。

五笔纯函数等有外部表之后再加。期望编码从那份表抄进测试，不从实现里导出。

### 真机

下列全部未验证，不能用假源或内部时间戳填：

- CH9329 把小键盘用法交给 Windows。
- 启用注册表之后，记事本得到“中”和“的”。
- 中文输入法两种模式下的结果。
- 松开 Alt 后菜单栏是否弹出。
- NumLock 熄灭时序列是否失效，以及 `GET_INFO` 的 bit 0 是否与灯一致。
- 浏览器、终端、远程桌面、UAC、密码框。
- BMP 以外的一个标量。
- 取消发生在 Alt 仍按下时，目标机上 Alt 是否抬起。
- macOS Unicode Hex Input 与 Linux Ctrl+Shift+U。

记录时写下操作系统版本、机器、采集模式和格式、串口速率、USB 拓扑、CH9329 配置。缺哪一项，该项就保持未验证。

### 最短手工步骤

这些步骤只检查目标机前提，不检查 KVMux。做的时候用目标机自己的键盘。

1. 用目标机上要接收按键的那个用户，把 `HKCU\Control Panel\Input Method\EnableHexNumpad` 设为字符串 `1`。注销并重新登录。仍无效时再重启。
2. 打开记事本。打开 NumLock。把中文输入法切到英文模式。
3. 按住左 Alt，按小键盘 `+`，用小键盘打 `7684`，松开 Alt。屏幕上应是“的”。看菜单栏有没有打开。
4. 再按住左 Alt，按小键盘 `+`，小键盘 `4`，主键盘 `e`，小键盘 `2`，主键盘 `d`，松开 Alt。屏幕上应是“中”。看编辑菜单有没有打开。
5. 把同一输入法切到中文模式，重复第 3 步和第 4 步。记下是汉字、候选窗，还是菜单。

第 3 步或第 4 步在任一模式下失败，就不要实现十六进制粘贴。五笔后备仍受上一节的码表限制。

## 默认决定

1. 主路径用 Windows 十六进制，五笔不进第一段。范围文字仍是五笔，要另一次修订才算改了产品范围。
2. 非法输入和码表没有的字，整段拒绝，不跳过。
3. 十六进制在 Windows 上按标量的十六进制一次发完，不补零，不拆代理。真机证明一次发完失败之后，才考虑代理对。
4. NumLock 未点亮或 LED 未知时拒绝开始，不改目标机的灯。
5. 只用左 Alt `0xE2`。取消和 `ReleaseAll` 走现有 `begin_clear`，不另做一套抬起。
6. 五笔若以后做，开始前由用户声明输入法配置和“当前是中文模式”。程序不探测。
